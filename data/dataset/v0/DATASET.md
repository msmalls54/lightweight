# Lightweight EMG curl dataset, v0

A small, honest dataset of curl reps measured with surface EMG (biceps + front delt, both arms), packaged so a small model (Gemma) can later be fine-tuned to **phrase** an AI coach's call-outs, and so a small strict-vs-swing classifier can be trained as a baseline. Nothing has been trained on it yet.

Regenerate everything from the raw recordings (deterministic, no network):

```
cd server && npx tsx scripts/export-dataset.ts
# options: --out <dir>, --no-synthetic, --db <server sqlite file> (adds stored live reps; skips replay sessions)
```

**Design rule (from the project): code decides, the model only phrases.** Whether a rep is a cheat is decided by the signal engine's thresholds (`server/src/engine/`). The Gemma pairs hand the model that verdict and ask only for the spoken line. They never ask the model to judge a rep.

## Collection setup

- **Sensors:** 4x SparkFun MyoWare 2.0 on 24 mm snap electrodes, Link Shield output on **ENV** (rectified + smoothed envelope, not raw EMG), into the MyoWare Arduino Shield on an Arduino UNO R4 WiFi, 14-bit ADC (0..16383; ENV saturates at ~14,960; rest ~500-900).
- **Channel map** (`peak_pct`/`mean_pct`/window index): `0` = R biceps (A0), `1` = R front delt (A1), `2` = L biceps (A2), `3` = L front delt (A3). Biceps is the target; the front delt is the "snitch" (it fires when the shoulder helps swing the weight). Pec, forearm and everything else are not sensed.
- **Placement:** biceps on the belly, in line with the fibers; delt 2 finger-widths below the bony shoulder tip, pointing down the arm (on Nov 13 this sat toward the middle delt). Shaved, alcohol-wiped. Battery powered.
- **Sample rate:** all three real recordings were logged at **~20 Hz** (Nov 13: fixed, `sample x 50 ms`; Nov 14: irregular, `t` in ms, ~33-60 ms steps). The live firmware streams 200 Hz; live DB rows come from that. Synthetic = 200 Hz.
- **Calibration** (`calibration` field, raw units): `pct = clamp((raw - rest) / (mvc - rest), 0, 1.5)`. Rest comes from the relaxed phases of each recording. **MVC is the ENV ceiling (14,960) on every channel**, because the 3 s max-flex holds under-read what curls reach (Nov 14 FLEX hold ~10,000 vs ~14,900 during curls) and the Nov 13 bench had no biceps MVC hold. So "%MVC" here is closer to "% of sensor range above rest". Nov 13 L channels were not worn and are fed as a constant 550 (their %MVC is 0).
  - Nov 13: rest `[570, 495, 550, 550]`. Nov 14 right: rest `[550, 620, 800, 900]`. Nov 14 bilateral: rest `[600, 620, 800, 900]` (the "ceiling" calibration in the tests).
- **How phases become sets** (same as the engine tests): Nov 13, each curl phase is its own engine session, fed in 4-sample batches. Nov 14, one session per file, one row per batch; the STRICT set runs from the STRICT label until the CHEAT label starts, the CHEAT set to the end of the file. Calibration/hold/relax phases outside sets produce no reps.

## Labels

Two labels per rep, deliberately **kept separate**:

- **`label_instructed`** (`"strict"` | `"swing"`): what the lifter was told to do in that phase (`strict_curls`/`STRICT` → strict, `cheat_curls`/`CHEAT` → swing). This is the closest thing to ground truth, but it is a per-phase instruction, not a per-rep judgment by an observer. A rep in a "swing" phase may be a light or failed swing (see the two disagreements above). For synthetic rows it is the generator's intent for the matched generator rep.
- **`engine_flag`** (bool) + **`engine_reason`** (`"delt_share_jump"` | `"delt_peak"` | null): the signal engine's verdict, with the thresholds in `server/src/engine/config.ts` at export time. Note the engine judges each rep against a **clean reference** learned earlier in the same set/session, so the same rep can get a different flag in a different session layout (Nov 13 swing rep 1 is flagged when the strict phase is fed first in the same session; here it is not, to match the tests' per-phase counts).
- `label_engine_agree` = (instructed == swing) == engine_flag.

**Label timing caveats.** The phase labels were typed by hand and are a few seconds off the movement:
- Nov 13: labels lag the movement. Each curl phase ends mid-rep (that rep is cut off: `had_rep_event: false` on Nov 13 swing rep 4, kept by `endSet`), and the following `rest` phase holds one more rep of each kind. Those trailing `rest` reps are **not** in v0 (the per-phase feed drops them).
- Nov 14 bilateral: labels lag. Strict reps 6 and 7 peak under the `relax4` label. They are kept in the STRICT set with `label_instructed: "strict"` and a `label_note` saying so; `phase_label_at_biceps_peak` shows the raw label.
- Nov 14 right arm: labels **lead** the movement by ~2.5-3 s. The reps still fall inside the right set, so no per-rep note.

## Schemas

### `reps.jsonl`

| Field | Meaning |
|---|---|
| `id` | `<recording_id>/set<set_index>/rep<rep>-<arm>`; shared by all three files (SFT ids add `/cue`) |
| `recording_id`, `source`, `person`, `session_id` | provenance. `source` is `"real"` or `"synthetic"` |
| `exercise`, `variant`, `load_lb`, `load_desc`, `arms_on` | what was lifted. `variant` is `standing` everywhere in v0. Band has `load_lb: null` |
| `arm` | `R`/`L`. For bilateral curls one rep event covers both arms; `arm` is the cheating arm if any, else the arm with the higher delt share. Both arms' numbers are in the 4-channel arrays |
| `set_index`, `set_label`, `rep` | 1-based set within the session, raw phase label (or preset name), 1-based rep within the set |
| `label_instructed`, `label_note`, `phase_label_at_biceps_peak` | instructed label and its caveat (see Labels) |
| `engine_flag`, `engine_reason`, `label_engine_agree` | engine verdict |
| `start_ms`, `end_ms`, `duration_ms`, `up_ms`, `down_ms` | rep window in engine time (device ms), time to 90% of biceps peak, time from the last 90% sample to the end |
| `peak_pct`, `mean_pct` | 4 channels, %MVC over the rep window |
| `delt_share` | `delt_mean / (delt_mean + biceps_mean)` for `arm` |
| `up_delt_ratio` | delt/biceps mean over the up phase only (biceps 30% → 90% of rep peak). The engine's main cheat feature under load |
| `baseline_delt_share`, `baseline_up_delt_ratio` | the clean reference the rep was judged against (`null` = none yet, only blatant reps can be flagged) |
| `r_share` | `R_bi_mean / (R_bi_mean + L_bi_mean)`; null with one arm |
| `had_rep_event` | false if the rep only appeared in the set end (cut off by the end of the set) |
| `sample_hz`, `calibration` | source rate and the rest/MVC used |

### `windows.jsonl`

Same `id`, provenance, context and label fields as `reps.jsonl`, plus `length` (128), `duration_ms`, `n_source_samples` (10-43 real samples at 20 Hz, so real windows are heavily upsampled), `sample_hz`, `channels` (`["R_biceps","R_front_delt","L_biceps","L_front_delt"]`) and `pct`: 4 arrays x 128 floats, %MVC, **linearly resampled in time** from `start_ms` to `end_ms` (so duration is normalized away; use `duration_ms`/`up_ms` as extra features if needed).

### `gemma_sft.jsonl`

`{"id", "kind", "source", "recording_id", ..., "messages": [{"role":"user","content":...},{"role":"model","content":...}]}` in Gemma chat roles (no system role: the instruction is in the user turn). Strip the metadata keys before training if your trainer wants `messages` only.

- **`kind: "rep_cue"`** (one per rep): user = exercise/load/arm/set/rep, the rep's numbers, and the **code verdict** (cheat yes/no + reason, imbalance from `r_share` vs 0.40-0.60, tempo from `up_ms` vs 300 ms). Model = the text of the pre-generated voice clips that `pickCueSequence(rep)` picks (`server/src/coach/cues.ts` + `CLIPS` in `server/src/voice/index.ts`), e.g. "Rep two. Your delt took over. Cheat rep." `cue_keys` holds the clip keys. Priority is cheat > imbalance > fast-up > rep count, all decided in code.
- **`kind: "set_summary"`** (one per set): user = `setFacts(set)` JSON (counts, cheat reps, delt shares, engine decision) and the instruction not to re-judge or change the weight. Model = `fallbackSummary(set)`, e.g. "4 reps, 3 cheats, delt took over from rep 2. Next set, stop at the first cheat and rest longer." `set_end_cue` is the set-end clip key.

Real cue lines are mostly rep counts and "delt took over"; the imbalance and slow-it-down lines come mostly from synthetic rows (plus a few real "right side's slacking" and "slow it down" calls from the 20 Hz data, which are what the code said, not verified observations).

## Limits

- **Tiny:** 28 real reps, 3 recordings, 1 person, 2 days, 1 lift (standing curls), 2 loads (band, 35 lb). No preacher or hammer curls yet. Any accuracy number on this is anecdotal; use leave-one-recording-out and report it per recording.
- **Relative, not medical:** %MVC is relative muscle activation for one person, one pad placement, one session. It is not force, not muscle growth and not a medical measurement. MyoWare is not a medical device. Don't compare numbers across sessions or people without recalibrating.
- **Label timing and granularity:** labels are per phase, hand-timed, seconds off the movement (see above). No observer labeled individual reps.
- **20 Hz real data:** the three real recordings are 10x coarser than the live firmware stream; windows, `up_ms`/`down_ms` are quantized to ~50 ms.
- **Engine version:** `engine_flag` reflects the thresholds at export time. Re-export after tuning the engine.
- **Sensor quirks:** the Nov 13 delt pad sat toward the middle delt; heavy curls saturate the biceps channel at the ENV ceiling.

## Intended use

1. **Distill an on-device Gemma coach voice.** Fine-tune a small Gemma on `gemma_sft.jsonl` so it can turn the engine's verdict and numbers into a short spoken line on-device, without a cloud LLM in the loop. The model never decides whether a rep was a cheat; the code does, and the prompt says so.
2. **Strict/swing classifier baseline.** Train a small classifier on `windows.jsonl` (or the scalar features in `reps.jsonl`) against `label_instructed`, and compare it with `engine_flag` on the same real reps. The engine is the bar to beat; synthetic rows are for pre-training/augmentation only.

Out of scope: medical or injury claims, force or strength estimates, judging people other than the calibrated wearer.

## Growth plan

- **Every live session already stores its raw batches in SQLite** (`batches` table) along with sets and reps. `--db` exports those reps today; a later version can replay the stored batches to emit 200 Hz windows too.
- **"Beat the agent" judge calls become human labels.** In the demo a judge whispers "clean" or "cheat" before each rep. Logging that call per rep gives a real per-rep human label, independent of both the phase instruction and the engine.
- More people (walk-ups, anonymized), more variants (preacher, hammer), and fresh calibrations per session, so the classifier and the voice model see more than one body.
